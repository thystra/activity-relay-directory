## Candidate scope

Activity-Relay Directory 1.2 improves relay discovery, long-term availability
tracking, and public directory presentation while preserving the authenticated
V1 Protocol and the frozen `/v1/relays` compatibility API.

The release candidate adds:

- discovery input compatibility for bare hostnames and non-default HTTPS ports;
- ActivityStreams `Group` relay actors;
- import classification that distinguishes duplicate input from relays already
  known through lifecycle or discovery state;
- `--add-dead-relays` retention for unavailable or incompatible candidates
  without treating them as verified relay actors;
- staged candidate retry at 6 hours, 12 hours, 24 hours, 3 days, then weekly,
  with promotion only after canonical actor validation succeeds;
- continued weekly recovery checks for long-term unavailable known relays;
- four public operational tiers with alphabetical ordering inside each tier;
- a 180-day Graveyard for relays not seen online for six months or longer;
- local tier-scoped exports and public plain-text relay host downloads; and
- user-focused README and public-directory documentation.

## Relay tiers and recovery

The richer public directory now groups verified known relays into four
operational tiers rather than ranking them by activity:

1. Tier 1 — current heartbeat and currently online;
2. Tier 2 — currently online without a current heartbeat;
3. Tier 3 — unavailable at the latest check but seen online within 180 days; and
4. Tier 4 — Graveyard, not seen online for at least 180 days.

Relays are alphabetical by hostname/actor inside each tier. Heartbeat frequency,
check recency, popularity, and traffic do not improve position. Graveyard relays
remain eligible for weekly recovery checks and automatically return to Tier 1 or
Tier 2 when they become reachable again.

Unverified candidates retained by `discovery import --add-dead-relays` remain
private until a later successful actor check validates and promotes them into
normal discovery state.

## Exports and public downloads

Operators can export the reviewed tiered projection locally with:

```sh
activity-relay-directory admin export --scope active --format hosts
activity-relay-directory admin export --scope unavailable --format hosts
activity-relay-directory admin export --scope all --format actors
```

When public listing is enabled, equivalent host lists are available at:

- `/downloads/active.txt` for Tier 1 and Tier 2;
- `/downloads/unavailable.txt` for Tier 3 and Tier 4; and
- `/downloads/all.txt` for all four tiers.

Host exports retain non-default HTTPS ports and can be fed back into discovery
import. Private provenance and unresolved retained candidates are not exposed.

## Default safety posture

Fresh installations remain deliberately inert until configured. Lifecycle,
public listing, reachability maintenance, automatic soft pruning, positive hard
retention, and administrator email all remain disabled by default. Enabling one
feature does not silently enable the others.

The public directory remains read-only. Moderation/source provenance, operator
reasons, signatures, nonces, private probe errors, client addresses, database
paths, and other administrative data remain outside the public projection.

## Source and release-build gates

Before canonical artifacts are built, run:

```sh
./scripts/acceptance-1.2.sh
```

That gate pins the released `v1.1.0` schema-8 baseline, verifies migrations 1
through 8 are unchanged and schema 9 is the only new migration, and exercises
1.2 discovery compatibility, retained-candidate retry/promotion, tier ordering,
Graveyard behavior, exports/downloads, and public API compatibility.

The normal Forgejo and GitHub validation workflows must also be green. GitHub's
package-validation job uses an explicit Ubuntu 26.04 runner so its debhelper
meets the package contract of version 13.25 or newer. Canonical release artifacts
remain Forgejo-authoritative and are built on the reviewed Debian Trixie release
profile.

## Candidate artifact and operator gates

After this source-preparation state is reviewed and merged, dispatch the Forgejo
canonical workflow against the exact merge commit with version `1.2.0-rc1` and
confirmation `BUILD 1.2.0-rc1`.

The exact generated Debian package and Docker archive must then be install-tested
independently with separate SQLite state and bind ports. Operator RC acceptance
must cover upgrade from 1.1/schema 8, real relay discovery/import, retained
unavailable candidates, the four public tiers, browser presentation, text
exports/downloads, lifecycle behavior, reverse-proxy/service logs, and rollback
readiness before tagging or publication.

Do not rebuild or relabel earlier release artifacts. Tagging, release
publication, deployment, activation, production verification, and stable 1.2.0
promotion remain separate explicit approvals.
