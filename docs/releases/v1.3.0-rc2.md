## RC1 findings addressed

The paired RC1 live exercise proved status-schema-4 capability advertisement,
Protocol-v2 registration, and relay-owned profile publication. RC2 keeps that
wire contract unchanged and addresses human-presentation findings from the live
review:

- the human relay card groups operator/registration information separately from
  relay focus;
- `participation_mode` is displayed as **Registration status**;
- `participation_url` is displayed as **About this relay**;
- relay type and topics appear under **Relay focus**;
- the language/country/region focus introduction and rows appear only when at
  least one of those fields is populated, so a general relay leaves the lists
  empty rather than advertising synthetic `any`, `all`, or `global` values; and
- an optional collapsed **Support this directory** block accepts up to eight
  provider-neutral support methods. Each entry has a title and exactly one
  absolute HTTPS URL or escaped plain-text value.

Support configuration is presentation-only. It is not emitted by `/v1/status`,
`/v1/relays`, or `/v2/relays`, and it cannot affect lifecycle, tiering,
moderation, reachability, pruning, enrollment, or public eligibility. HTML,
Markdown, scripts, remote embeds, pixels, and other third-party support content
are not accepted.

## Paired live gate

Deploy ARD `1.3.0-rc2` first, then Activity-Relay `3.1.0-rc2`. Confirm:

1. `/v1/status` still advertises lifecycle versions `[1,2]`;
2. the existing relay remains in the same operational tier;
3. its profile renders with the new labels/grouping;
4. empty language/country/region lists suppress the focus subsection;
5. setting one of those lists makes the focus subsection appear;
6. configured support methods render only on the human Directory page;
7. `/v1/status`, `/v1/relays`, and `/v2/relays` contain no support metadata; and
8. profile sync, heartbeat, explicit clears, precedence, and v1 fallback remain
   unchanged from RC1.

Any new production-code change requires another release candidate.
