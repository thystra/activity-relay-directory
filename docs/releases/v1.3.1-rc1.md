Status: prerelease candidate; not published or deployed.

- Application version: `1.3.1-rc1`
- Debian package version: `1.3.1~rc1-1`

- Lifecycle protocols: 1, 2 and 3 (when enabled)
- Previous stable release: `v1.3.0`

## Scope

The unreleased 1.3.1 reachability diagnostics remain, including safe DNS,
connect, TLS, actor and inbox observations. RC1 adds a bounded per-relay
**consecutive actor failure streak**, saved in SQLite schema 14.

After a healthy actor becomes unreachable, the next eligible checks are:
1 hour after the first failure, 2 hours after the second, 4 hours after the
third, then 6 hours for the fourth and subsequent failures. A successful actor
probe resets the streak and restores the ordinary six-hour cadence. A relay
with no positive online evidence for seven days retains the existing weekly
retry schedule. The worker continues running approximately hourly; eligibility
is not a guarantee of execution at the exact minute.

RC1 also treats a current accepted, authenticated heartbeat as independent
positive evidence of relay liveness. A relay with a healthy heartbeat but
unreachable actor now belongs in Tier 2 (one positive signal), not Tier 3.
Tier 1 still requires **both** current authenticated liveness and a recent
successful actor check. Actor check failure remains published independently as
`reachability.state=unreachable`, along with the structured diagnostic. Tier 3
and Tier 4 require neither current signal. Summary online/offline counts and
active/unavailable download sets use the same definitions as the tier listing.

This is not a claim that the actor endpoint or inbox is serving requests, and
it does not alter moderation, enrollment, authenticated heartbeat timestamps,
actor security checks, protocol signatures, soft pruning or hard retention.

## Upgrades and rollback

Schema 14 only adds the bounded streak and adjusts retry eligibility for
recently failed rows. Migrations 1–13 are immutable.

**Hermod already ran an unreleased `1.3.1-1` candidate.** Debian orders
`1.3.1~rc1-1` *below* `1.3.1-1`, so deploying RC1 over that existing package
is a Debian package-version downgrade, even though the database schema advances
from 13 to 14. Do not rely on an automatic upgrade: require a reviewed explicit
package installation with downgrade authorization, a verified pre-upgrade SQLite
backup, and a matching restore procedure. Do not install the RC on
production without a verified online SQLite backup and restoration plan. Once
migrated to schema 14, downgrading to schema 13 requires restoring the matching
pre-upgrade database; package removal alone does not downgrade SQLite.

Fresh installs remain disabled by default. Package upgrades do not restart an
operator-enabled service automatically. Build and install-test the exact
canonical artifact set before signing or publishing `v1.3.1-rc1`.
