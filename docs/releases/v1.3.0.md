## Stable scope

Activity-Relay Directory 1.3 promotes the accepted 1.3.0-rc4 behavior to stable
without runtime changes. The 1.3 line adds reviewed descriptive relay profiles,
CSV exchange, negotiated lifecycle Protocol v2/v3 support, bounded
participating-site telemetry, and operator-facing presentation improvements
while keeping operational evidence separate from descriptive metadata.

Lifecycle, public listing, background reachability, automatic pruning, and hard
retention remain independently controlled. Fresh installations keep the same
conservative default-off behavior.

## Relay profiles and CSV exchange

Schema 10 introduced source-scoped descriptive relay profile assertions and
private append-only history. Effective values resolve independently per field
with fixed precedence:

```text
override > relay > csv
```

The local CSV import/export path is bounded and spreadsheet-safe. CSV profile
changes do not refresh heartbeat evidence, create reachability, alter moderation
or enrollment, or change public tier eligibility. `participation_mode` values
used for registration badges and filters are case-sensitive in 1.3.0 and should
be exact lowercase `open`, `restricted`, `closed`, or empty.

An exact actor already retained as an active lifecycle or discovery identity may
receive a CSV profile replacement even when its current actor probe fails. This
allows an operator to maintain descriptive metadata for an unavailable relay
that is already legitimately present in the Directory. Unknown candidates still
require the normal actor-validation path or explicit `--add-dead-relays`
retention and do not gain public/profile identity from CSV alone.

Production RC4 validation exercised this behavior with an existing unavailable
relay: preflight classified it as already known, reported the intended
`participation_mode`/`availability` changes, and applied the CSV source without
fabricating operational evidence.

## Lifecycle Protocol v2 and v3

Protocol v2 adds authenticated complete-profile synchronization on register while
heartbeat and unregister remain identity-only. Protocol v3 retains that profile
contract and may additionally carry bounded `participating_instance_count`
telemetry. `/v1/status` advertises the explicitly supported lifecycle versions;
Protocol v1 remains available for compatibility.

Schema 11 stores the earlier receiving-instance telemetry and schema 12 stores
Protocol-v3 participating-instance telemetry separately. Public **Sites** prefers
the v3 participating count and falls back to the older receiving count during
rolling upgrades. Telemetry is informational only and cannot affect tiering,
moderation, enrollment, reachability, pruning, or public eligibility.

Every successful authenticated registration is current liveness evidence. Create,
unchanged/profile-sync, and restore registration outcomes advance the retained
heartbeat timestamp as well as lifecycle last-seen time. Explicit heartbeat does
the same. CSV, discovery, profile-only local writes, moderation, and reachability
checks do not fabricate that evidence.

RC4 production acceptance with Activity-Relay confirmed that a normal relay
restart emitted a fresh authenticated heartbeat and returned the relay to Tier 1
without requiring a configuration edit.

## Public Directory

`/v2/relays` schema 5 publishes the reviewed effective profile together with
bounded relay telemetry and the existing independent heartbeat/reachability
evidence. The human Directory uses the same projection. Registration status is
displayed as Open, Restricted, Closed, or Not reported and can be filtered
without changing operational tier placement.

The four public tiers remain operational, non-prestige classifications:

1. Tier 1 — current authenticated liveness and current reachability;
2. Tier 2 — reachable without current authenticated liveness;
3. Tier 3 — currently unavailable but seen online within 30 days; and
4. Tier 4 — Graveyard, not seen online for at least 30 days but retained for
   history and recovery checks.

Descriptive profile data and self-reported telemetry cannot move a relay between
those tiers.

## Operator presentation and documentation

The package-managed operator reference is
`/etc/activity-relay-directory/config.yml.example`. The live
`/etc/activity-relay-directory/config.yml` remains operator-owned and is neither
created nor overwritten by the package. Optional Directory title, HTTPS banner,
operator-contact, and support settings are presentation-only.

The project README is intentionally concise. Deployment guidance lives in
`docs/INSTALLATION.md`, normal CLI/operator procedures in
`docs/ADMINISTRATION.md`, and contributor/test procedures in
`docs/DEVELOPMENT.md`; detailed protocol, storage, security, discovery, profile,
moderation, retention, and release contracts remain topic-specific documents.

## Packaging and canonical artifacts

The Debian package version is `1.3.0-1`. Package upgrade preserves Directory
state and does not automatically restart an operator-activated service; after
reviewing the upgraded package/configuration, restart deliberately to load the
new binary. In-place SQLite downgrade is unsupported and requires restoring the
backup matching the older release.

The Forgejo canonical workflow wraps `public/` and `evidence/` in the
deterministic `activity-relay-directory-canonical.tar` carrier before Actions
artifact upload. Public `SHA256SUMS` remain the checksum authority for the
release assets while the carrier preserves expected Unix modes and deterministic
release timestamps across the outer artifact transport.

Stable `1.3.0` is built as a new canonical artifact set from the stable-promotion
commit. Accepted RC4 artifacts are not renamed or relabeled as stable release
files.

## Compatibility and data safety

The stable release preserves the frozen `/v1/relays` compatibility contract and
Lifecycle Protocol v1 while adding v2/v3 routes and richer `/v2/relays` output.
Existing schema-9 through schema-11 databases upgrade in place through the
reviewed migrations to schema 12. Historical migrations remain immutable.

Unavailable and Graveyard relays are retained for recovery by default. Reversible
soft pruning remains distinct from destructive hard retention. Hard retention
continues to default to disabled and requires the existing verified-backup gate
before destructive execution.

## Release acceptance

The accepted RC4 line passed authoritative CI, cross-repository Protocol v2/v3
fixtures and live interoperability, authenticated registration/heartbeat liveness
checks, public Tier-1 recovery, populated CSV/profile operation, known-offline
relay metadata replacement, and package/configuration validation. Stable
`1.3.0` must now receive its own canonical build and artifact-transport
validation, and publication must use the exact canonical bytes built from the
reviewed stable-preparation commit.
