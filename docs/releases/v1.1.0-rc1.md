## Candidate scope

Activity-Relay Directory 1.1 adds operator-controlled discovery and independent
relay reachability without changing the authenticated version 1 lifecycle or
reinterpreting heartbeat recency. Schema version 8 records discovery state,
actor/inbox observations, and positive RFC 9421 evidence while preserving
private provenance and audit boundaries.

The candidate adds:

- local `admin discovery add|remove|import` commands with bounded candidate
  input, SSRF-resistant actor verification, private provenance, and one
  non-mutating inbox diagnostic;
- default-off bounded background actor/inbox reachability maintenance with
  fixed hourly scheduling, six-hour evidence freshness, at most 96 actors per
  run, and at most eight concurrent probes;
- fresh-reachability protection for soft pruning, including a fail-closed
  complete-coverage gate;
- default-off `GET /v2/relays` plus the human `/` view over one bounded v2
  projection containing heartbeat, reachability, inbox-diagnostic, and positive
  RFC 9421 evidence; and
- retention-policy version 2 integration for the newly introduced
  identity-bearing discovery and observation state.

- `/v2/relays` schema: `2`.

Migrations `0001` through `0007` remain byte-identical to the `v1.0.0` release;
`0008_discovery_reachability.sql` is the only new migration. Existing retained
lifecycle/audit state upgrades in place to schema 8. In-place database downgrade
is unsupported: take and verify a standalone SQLite backup before upgrade, and
restore the matching older backup when downgrading.

## Public and privacy contract

`/v1/relays` retains the 1.0 wire and semantic contract. The new v2 projection
keeps lifecycle heartbeat, actor reachability, inbox diagnostics, and RFC 9421
evidence independent. Discovered-only relays never receive fabricated
registration or heartbeat timestamps. Administrative suspension overrides both
registration and discovery eligibility.

Discovery source/provenance, operator and reason values, private probe errors,
audit events, database identifiers, request signatures, client addresses,
resolver details, and internal participation flags remain non-public.

## Default safety posture

Fresh installations remain deliberately inert until configured. In particular:

- lifecycle routes remain disabled by default and enrollment remains closed;
- public directory presentation remains disabled by default;
- background reachability remains disabled by default;
- automatic soft pruning remains disabled by default;
- inactive-record retention remains `0` (indefinite); and
- administrator email remains disabled.

Enabling the public listing does not activate lifecycle, reachability, pruning,
retention, or any public mutation route.

## Source acceptance

Tranche 23 source acceptance exercises twelve reviewed cases through
`scripts/acceptance-1.1.sh`, including exact 1.0.0/schema-7 upgrade identity,
registered and discovered-only participation paths, candidate URL convergence,
fail-closed resolver/network behavior, inbox method rejection, a real RFC 9421
signed lifecycle request persisted through SQLite, independent
registration/discovery transitions, suspension, pruning races, and schema-8
inactive retention.

The accepted source gate also passed formatting, `go vet`, the complete normal
and race test suites, native build, v1 compatibility checks, and the normal
Forgejo Buildx validation container build before merge to `master`.

## Candidate artifact and operator gates

Forgejo is authoritative. After this candidate-preparation source state is
reviewed and merged, the manual exact-commit workflow must build a new canonical
1.1.0-rc1 artifact set. The Debian package and Docker archive from that one set
must then be independently install-tested using separate SQLite state and bind
ports before tagging or publication.

Do not relabel 1.0.0 artifacts. Tagging, release publication, deployment,
activation of the default-off 1.1 surfaces, production verification/soak, and
stable 1.1 promotion remain separate explicit approvals.
