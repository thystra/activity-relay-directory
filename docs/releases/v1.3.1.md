## What changed

Version 1.3.1 adds bounded **reachability diagnostics** for relay actor and
inbox checks. The Directory can now distinguish DNS resolution, connection,
TLS, redirect, HTTP response, malformed actor, and non-mutating inbox `OPTIONS`
outcomes instead of reporting every problem as an undifferentiated outage.

When an actor returns HTTP 404 or 410, or DNS lookup indicates that the name
may no longer exist, the Directory can mark it **possibly removed**. This is
an interpretation of one observation, **not** evidence sufficient to delete
the relay. Transient failures such as timeouts and HTTP 5xx responses are not
presented as confirmed decommissioning.

The human Directory shows diagnostic evidence in expanded relay details.
`/v2/relays` schema 6 adds optional bounded `diagnostic` objects beneath actor
reachability and inbox state, and the earliest eligible time for a background
recheck. A diagnostic includes a stage, code, optional HTTP status, and
cautious assessment; it does not contain DNS addresses, raw exceptions,
response bodies, or private discovery provenance.

A network-error handling correction also keeps ordinary DNS and connection
outages separate from prohibited destination-policy failures. As a result,
`--add-dead-relays` can retain an unreachable candidate when the normal
import policy permits it, without treating an ordinary outage as a forbidden
target.

## Behavior and compatibility

- SQLite migration 13 adds `relay_probe_diagnostics` without modifying the
  earlier migrations. It does not invent diagnostic history for existing rows.
- Diagnostics do not change authenticated participation/liveness evidence,
  moderation, enrollment, relay eligibility, public tier placement, pruning,
  or hard retention decisions.
- Failed actor checks retain the previous successful actor timestamp and
  previously observed inbox evidence. The latest inbox observation may be older
  than the latest actor check and is labeled accordingly.
- The normal background recheck interval remains six hours; relays offline for
  at least seven days retain the seven-day retry policy. The published next
  eligible time is not a promise that a check has already been scheduled or run.
- Inbox probing remains non-mutating `OPTIONS`. HTTP 405/501 is method
  rejection, not proof that delivery is unsupported.
- `/v1/relays`, lifecycle Protocols 1/2/3, and the four operational tiers
  remain compatible with 1.3.0. The V2 public API schema advances from 5 to 6.
- Activity-Relay ban/block-list coordination is **not** part of this release.

Detailed field definitions and cautions are in
[`docs/REACHABILITY-DIAGNOSTICS.md`](../REACHABILITY-DIAGNOSTICS.md) and
[`docs/PUBLIC-LISTING.md`](../PUBLIC-LISTING.md).

## Installation and upgrade

The Debian package version is `1.3.1-1`. An upgrade preserves the existing
Directory data, operator-owned configuration, and running service; the package
does not automatically restart an operator-activated daemon. After reviewing
the package and configuration, the operator must deliberately restart the
service to load the new binary.

**Back up and restore-test the production SQLite database before starting
1.3.1 against it.** First startup applies schema 13 before opening the HTTP
listener. In-place database downgrade is unsupported: rollback to 1.3.0 after
migration requires the corresponding pre-upgrade database backup and 1.3.0
binary. Maintain the existing disabled-by-default configuration and current
retention policy; this release does not authorize automatic hard removal.

Fresh installations keep the established conservative defaults. Only the
Forgejo canonical release workflow produces authoritative Debian, standalone
binary, CycloneDX SBOM, build metadata, Docker image archive, and SHA256SUMS
assets. A review and installation test of that exact artifact set must occur
before tagging/publication.

## Release acceptance

The feature source passed Go 1.26.0 unit tests, `go vet`, and race-enabled tests
on the maintainer's Fafnir workstation. The reviewed changes include resolver
redaction and classification regressions, diagnostic persistence/retention,
long-offline retry handling, and public presentation tests.

Publication and Hermod deployment remain **separate pending gates**: run the
1.3.1 source acceptance script, validate packaging and exact canonical bytes,
verify backup/restore and schema migration, then obtain operator approval for
publication and a deliberate production upgrade.
