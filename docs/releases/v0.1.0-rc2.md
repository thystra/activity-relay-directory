# Activity-Relay Directory 0.1.0-rc2

Status: release-candidate draft. This document is committed before publication;
the candidate is not released until the separate canonical-artifact,
installation-acceptance, operator-acceptance, tag, and publication gates
succeed.

## Version identity

- Git tag: `v0.1.0-rc2`
- Application version: `0.1.0-rc2`
- Debian package version: `0.1.0~rc2-1`
- Previous published candidate: `v0.1.0-rc1` (immutable)
- First eventual stable version: `1.0.0` / Debian `1.0.0-1`
- There will be no final `v0.1.0` tag.

## Candidate scope

RC2 is a corrective candidate following operator/browser review of RC1. It
retains the version-1 lifecycle protocol, schema version 7 storage model,
moderation, health projection, pruning, retention, growth-budget, and
administrative behavior from RC1. This candidate does not introduce a protocol,
database-schema, lifecycle-state, or storage-contract change.

## Public Directory correction

The human `GET /` view is treated as a public product surface. It uses the same
bounded filtered projection as the JSON directory while presenting an
Activity-Relay-family layout, intentional empty state, relay cards, health
context, and secondary JSON access.

The application owns its route-specific Content-Security-Policy. Reverse-proxy
examples no longer add a generic `default-src 'none'` CSP that intersects with
the application's HTML policy and blocks the bundled same-origin stylesheet.
The page remains dependency-free: no JavaScript, remote fonts, analytics,
third-party scripts, or relay-controlled image fetches are required.

## Accessibility

Health status never depends on color alone. The visible words `healthy`,
`stale`, and `dead` remain present and are reinforced by distinct symbols and
border treatments. Development tests retain reviewed light/dark text contrast
coverage of at least 4.5:1 and non-color state-cue regression coverage.
Protanopia, deuteranopia, and tritanopia palette simulation remains a design
diagnostic rather than a substitute for those semantic cues or human browser
review.

## Release-candidate acceptance

Development validation remains automated and implementation-aware. RC
acceptance is operator-guided and records `PASS`/`YES`, `FAIL`/`NO`, `RETRY`,
optional `SKIP`/`N/A`, and `ABORT`. A noncritical `FAIL`/`NO` is recorded as
evidence and does not automatically stop the session; explicitly critical
safety/identity/startup failures abort.

The RC2 operator pass must include a real browser review of the public page and,
when Activity-Relay integration is ready, representative registration,
visibility, moderation/suspend/restore, and operator-console workflows.

## Installation and artifact authority

Forgejo remains authoritative. The canonical workflow builds one exact artifact
set from the reviewed RC2 source commit: Debian package, standalone binary,
CycloneDX SBOM, build metadata, Docker-loadable `linux/amd64` image archive, and
one checksum manifest.

The manual canonical preflight treats dispatch strings as quoted data, validates
the requested commit/candidate identity, explicitly installs its Debian
packaging tools, and only then parses the changelog candidate version before
build work.

Before `v0.1.0-rc2` may be created, the exact canonical Debian package and Docker
archive must be independently install-tested with separate writable SQLite
state. Package installation remains separate from activation and must leave the
systemd service disabled/inactive until explicit operator action. Public
exposure, lifecycle/listing activation, tagging, and release publication remain
separate gates.

RC1's tag and published bytes are not modified or replaced by this candidate.
