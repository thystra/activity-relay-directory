## What changed

The website calls the existing opt-in authenticated lifecycle protocol the
**ARD White Pages Protocol**. Its four visible listing headings are **ARD White
Pages Protocol Relays**, **Other Known Relays**, **Offline or Unreachable
Relays**, and **Graveyard**. The numeric `tier` values 1–4 remain in the JSON API
and internal logic. The second group can include White Pages participants with
a healthy heartbeat but a failed Actor check. An Actor or heartbeat failure
alone is not proof that a relay is offline.

The public Directory uses **ActivityPub Actor** and **ActivityPub Inbox** in
checks and explanatory labels. An Actor endpoint identifies a relay; an Inbox
receives ActivityPub messages. The page explains the difference without
requiring visitors to know the ActivityPub protocol.

Heartbeat badges show just **Healthy**, **Stale**, or **No heartbeat received**.
The API keeps its five existing heartbeat state codes; an overdue heartbeat
can display **Stale** even for a relay in the **Graveyard**. A relay's tier is
still calculated from current authenticated heartbeat evidence and recent
successful Actor checks, independently of the displayed heartbeat wording.

Diagnostics now describe what the check observed, using understandable DNS,
connection, redirect, ActivityPub Actor, and ActivityPub Inbox messages.
Certificate verification and HTTPS handshake failures explicitly say
**TLS error** without suggesting that the relay is permanently offline.

The ActivityPub Inbox check now displays its actual observation time when
available and says message delivery was not tested. An HTTP 405 or 501 means
the Inbox does not support that particular check; it does not establish that
ActivityPub delivery is unavailable.

## Compatibility and upgrades

RC2 is a presentation and documentation update over RC1. It does **not** change
SQLite migrations, data, heartbeat/reachability measurement, retry intervals,
soft pruning, retention, lifecycle authentication, HTTP `/v1/relays`, or the
machine-readable `/v2/relays` schema 6 values.

Standard Debian package upgrades from the released `1.3.1~rc1-1` to
`1.3.1~rc2-1` follow the normal version order. Preserve existing operator
configuration, verify database backups, review the service status, and follow
the documented restart policy. As of RC2, package maintainer scripts do not
explicitly restart an already-running service on upgrade; some host tools
(such as `needrestart`) may restart it separately. Plan for this possibility.
Rollback across schema versions requires restoring the corresponding pre-upgrade
SQLite backup; no schema change is expected between RC1 and RC2.
