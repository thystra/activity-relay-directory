Status: stable release draft.

- Git tag: `v1.2.0`
- Application version: `1.2.0`
- Debian package version: `1.2.0-1`
- Accepted release-candidate source: `f29ab23c372871f6f046f5a4f415ebded1e44f87`
- Previous stable release: `v1.1.0`

## What's new in 1.2

Activity-Relay Directory 1.2 expands operator discovery, long-term relay
availability tracking, and the public-facing Directory while preserving the
authenticated V1 Protocol and the frozen `/v1/relays` compatibility API.

The accepted `1.2.0-rc2` behavior is being promoted to stable without runtime
behavior changes. Stable `1.2.0` will be built and published as its own release;
accepted RC2 artifacts are not relabeled as stable files.

## Relay discovery and retained candidates

Discovery imports accept bare hostnames, non-default HTTPS ports, base URLs,
`/actor`, and `/inbox` candidate forms while continuing to require canonical
actor validation before a relay becomes verified public state. ActivityStreams
`Group` actors are accepted alongside the previously supported relay actor
types.

Imports distinguish duplicate input from relays already known through lifecycle
or discovery state. Existing identities are not duplicated or rewritten merely
because they appear in another import.

`discovery import --add-dead-relays` can retain unavailable or incompatible
candidates privately for later checks. Retry timing is 6 hours, 12 hours, 24
hours, 3 days, and then weekly. A retained candidate remains outside the public
relay listing until a later successful actor validation promotes it.

## Public relay tiers and recovery

Verified known relays are grouped into four operational tiers rather than
ranked by popularity:

1. Tier 1 — current Directory heartbeat and currently online;
2. Tier 2 — currently online without a current heartbeat;
3. Tier 3 — offline or unreachable at the latest check but seen online within
   the last 30 days; and
4. Tier 4 — Graveyard, not seen online for at least 30 days.

Relays are alphabetical inside each tier. Heartbeat frequency, check recency,
popularity, and traffic do not improve position. Graveyard relays remain in the
database and continue periodic recovery checks; successful recovery moves them
back to Tier 1 or Tier 2 automatically.

The public-facing Directory page summarizes the number of verified relays known,
currently online, currently offline, and unresolved candidates pending
verification. Only the pending count is public: candidate identities, failure
details, source labels, and other discovery provenance remain private.

## Exports and public downloads

Operators can export the tiered public relay set locally with:

```sh
activity-relay-directory admin export --scope active --format hosts
activity-relay-directory admin export --scope unavailable --format hosts
activity-relay-directory admin export --scope all --format actors
```

When public listing is enabled, plain-text host lists are also available at:

- `/downloads/active.txt` for Tier 1 and Tier 2;
- `/downloads/unavailable.txt` for Tier 3 and Tier 4; and
- `/downloads/all.txt` for all four public tiers.

Host exports preserve non-default HTTPS ports and can be fed back into a later
discovery import. Private provenance and unresolved candidate identities are not
exported.

## Compatibility and schemas

Compatibility versions for 1.2 are:

- database schema: `9`;
- `/v1/status` schema: `3`;
- `/v1/relays` schema: `1`, frozen for 1.0 compatibility;
- `/v2/relays` schema: `3` with cursor format version `2`;
- lifecycle protocol: version `1`; and
- Go module floor: `1.26.0`.

Migrations `0001` through `0008` remain byte-identical to the `v1.1.0` release.
`0009_discovery_candidates.sql` is the only 1.2 migration. Existing schema-8
databases upgrade in place to schema 9. In-place downgrade is unsupported; take
and verify a standalone SQLite backup before upgrading and restore the matching
older backup when returning to an older binary.

## Debian package upgrades

Package upgrades preserve the current service enablement state and do not stop
or restart an operator-activated Directory. Package configuration reloads
systemd's unit definitions automatically so the installed unit is current.
After reviewing the upgraded package and configuration, restart the service
manually when you are ready to load the new binary.

Normal package removal preserves the Directory database and dedicated service
account. Explicit package purge remains the destructive boundary.

## Safe defaults

Fresh installations remain deliberately inactive until configured. Lifecycle,
public listing, background reachability maintenance, automatic soft pruning,
positive hard retention, and administrator email all remain disabled by
default. Enabling one feature does not silently enable the others.

The public Directory remains read-only. Moderation/source provenance, operator
reasons, signatures, nonces, private probe errors, client addresses, database
paths, and other administrative data remain outside public output.

## Release acceptance

The accepted RC2 source passed the 1.2 source acceptance matrix, including
schema identity, discovery compatibility, candidate retry/promotion, tiering and
30-day Graveyard behavior, exports/downloads, and public API compatibility.

Canonical RC2 acceptance also verified exact checksums, Debian RC1-to-RC2
upgrade without an automatic service restart, automatic systemd daemon reload,
manual restart into RC2, live schema-9 state, the public aggregate summary, and
Docker fresh-volume plus persistence/recreate behavior. Stable 1.2.0 remains a
separate canonical build from the stable-promotion source commit.
