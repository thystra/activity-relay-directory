## Candidate scope

Activity-Relay Directory 1.3 adds descriptive relay profiles while preserving
the separation between relay/operator claims and Directory-observed operational
evidence. Profile content does not determine lifecycle state, reachability,
moderation, public eligibility, pruning, or public tier.

The release candidate adds:

- schema 10 source-scoped relay-profile persistence and private history;
- per-field effective precedence `override > relay > csv > absent`;
- bounded CSV import/export with deterministic semicolon/backslash list
  escaping and reversible spreadsheet formula-injection protection;
- `/v2/relays` schema 4 effective profile projection and matching human-page
  rendering with source provenance kept private;
- lifecycle Protocol v2 on `/v2/relays/register`, `/heartbeat`, and
  `/unregister`;
- a dedicated `activity-relay-directory-v2` RFC 9421 signature tag;
- complete relay-owned profile replacement on v2 register while v2 heartbeat
  and unregister remain identity-only; and
- `/v1/status` schema 4 capability advertisement through ordered
  `lifecycle_protocol_versions`.

Protocol v1 and `/v1/relays` remain compatibility contracts and are not
redefined by 1.3.

before upgrading and restore the matching older backup when rolling back.

## Profile ownership and precedence

Each profile field is resolved independently in this order:

1. local operator override;
2. authenticated relay self-report;
3. CSV assertion;
4. absent.

A Protocol-v2 register sends the complete relay-owned profile. Empty strings and
empty arrays clear the relay-owned assertion for those fields; they do not
delete CSV or operator assertions. Removing a higher-priority assertion exposes
the next lower-priority source again.

CSV import requires a header row. `relay` is required, column order may vary,
`source_url` is optional, and duplicate or unknown columns are rejected.

## Source acceptance gate

Before canonical artifacts are built, run:

```sh
./scripts/acceptance-1.3.sh
```

The gate verifies that migrations 1 through 9 are unchanged from `v1.2.0`,
schema 10 is the only new migration, source precedence and clear behavior are
correct, CSV round-trip/formula protection holds, public projection remains
private and operationally independent, Protocol v1 remains accepted, and the
shared Protocol-v2 fixture persists the relay-owned profile while status schema
4 advertises versions `[1,2]`.

The normal Forgejo source, race, package, and container validation workflows
must also be green on the exact RC-preparation commit.

## Paired Activity-Relay 3.1 live gate

RC acceptance is cross-repository. Deploy the accepted ARD RC1 artifacts first,
then deploy the paired Activity-Relay 3.1 RC1 artifacts to a controlled live
relay. Preserve the exact artifact bytes and source identities used for the
exercise.

Required live evidence:

1. `GET /v1/status` returns schema 4 and advertises lifecycle versions `[1,2]`;
2. Activity-Relay performs capability discovery and sends a signed
   `POST /v2/relays/register`;
3. the registered twelve-field profile is visible through the effective
   `/v2/relays`/human projection without exposing source provenance;
4. changing `DIRECTORY_PROFILE` and running explicit Directory sync updates the
   relay-owned profile immediately;
5. empty scalar/list values clear only relay-owned assertions and reveal lower
   CSV assertions when present;
6. an operator override masks relay and CSV values, and removing it reveals the
   relay value again;
7. heartbeat leaves profile values unchanged;
8. profile changes do not alter tier, public eligibility, reachability,
   moderation, pruning, or enrollment;
9. unregister/re-register converges without corrupting retained profile source
   state; and
10. a v1-only lifecycle client continues to register/heartbeat successfully
    against the same ARD RC.

Any production-code change discovered during this exercise requires another
release candidate.
